Цель: компенсировать слабые стороны ИИ (пространственное воображение, арифметика, самопроверка) инструментами: однозначные единицы, понятные ошибки, ссылки на геометрию по смыслу, автоматические проверки требований.

## P2-T1 — Аудит единиц измерения (документ)

### Контекст (проверено)

### Задача
Создай `docs/UNITS.md`:
1. Таблица «где какие единицы» для каждого MCP-инструмента (вход и выход): `grep` по `crates/mcp-cad-server/src/tools/*.rs` и схемам в `tools/mod.rs`; для каждого поля — единица, если она задана, или «не указана».

3. Предложение контракта. Рекомендуемый вариант по умолчанию: единицы на границе API задаются проектом (`length_unit`: `mm` по умолчанию, `m` допустимо; сила — Н; напряжение — МПа; масса — кг; время — с), внутри ядра остаётся СИ, конвертация только в слое `tools/*.rs`. **[DECISION]** Подтвердить выбор единиц по умолчанию.
4. Проверка масштаба: список эвристик предупреждений («габарит > 10 м или < 0.1 мм — вы уверены в единицах?»).
5. Список мест кода, которые придётся изменить, с оценкой размера (S/M/L).

### Критерии приёмки
Каждый пункт заполнен; ссылки на код проверены; нет предложений без указания затронутых файлов.

### Критерии приёмки

### Задача

## P2-T8 — FEA: граничные условия по именам граней

**Размер:** M | **Зависит от:** P2-T7 | **Ветка:** `agent/P2-T8`

### Контекст (проверено)
`run_fea_analysis` (`crates/mcp-cad-server/src/tools/fea.rs`) принимает `fixed_faces: [str]` (AABB-имена), `fixed_plane`, `applied_forces`. В `boundary.rs` — `BoundaryConditions::{fix_plane, fix_aabb_face, fix_nodes, add_nodal_force, add_area_force, add_aabb_face_force}`, `resolve(&TetrahedralMesh)`. Тетра-сетка воксельная (`tetra_mesh.rs`, ≤60 ячеек на ось), узлы лежат на ступенчатой границе, а не на исходных гранях.

### Задача
1. Новые параметры: `fixed: [{"face":"<имя>"}|{"where":{…}}]`, `loads: [{"face":"<имя>","force":[Fx,Fy,Fz]}|{"face":…,"pressure":p}|{"face":…,"moment":…}]`, старые параметры оставь рабочими.
2. Сопоставление граней с узлами тетра-сетки: узел считается принадлежащим грани, если он лежит в пределах допуска (≈ размер элемента) от поверхности этой грани (по исходной сетке; используй расстояние до треугольников грани).
3. Если грань не нашлась или ни один узел не попал — понятная ошибка с подсказкой (используй формат из P2-T3, если он уже есть).
4. Сумма приложенных сил равна заданной (допуск 1e-9 относительный), распределение по узлам пропорционально площадям.

### Критерии приёмки
- Тест: цилиндрический вал, закреплён один торец, нагрузка на другой — совпадение осевого растяжения с `σ = F/A` в пределах допуска, который уже используется в `fea_tests.rs` для осевого растяжения.
- Тест: нагрузка по грани отверстия.
- Все существующие FEA-тесты проходят.

## P2-T9 — Слой требований: `set_requirements` / `check_requirements`

**Размер:** M | **Зависит от:** P2-T2 | **Ветка:** `agent/P2-T9`

### Идея
Агент плохо проверяет себя сам. Пусть он ОБЪЯВЛЯЕТ требования один раз, а система проверяет их после каждого изменения и возвращает измеренные значения и запасы. Это превращает «кажется, получилось» в «PASS/FAIL с числами».

### Контекст (проверено)
Уже есть строительные блоки: габариты и объём — `list_parts`/`query_part_geometry`, масса — материал×объём, валидность — `validate_mesh`, прочность — `run_fea_analysis` (`FeaReport.factor_of_safety`), коллизии — `SimulationSummary` (физика). Инструменты регистрируются в `tools/mod.rs` (определение `ToolDefinition` + ветка в `dispatch_tool`). Для устаревания кэша добавь счётчик `revision: u64` в `Part`, увеличиваемый на каждое изменение DAG/трансформации (`#[serde(default)]`).

### Задача
1. Инструмент `set_requirements(part_id | scope:"scene", requirements:[…])` и `check_requirements(part_id?)`. Типы требований: `bbox_max {dims}`, `bbox_min {dims}`, `mass_max {kg}`, `mesh_valid`, `min_safety_factor {value, fea_case?}`, `no_interference {pairs?}`, `mechanism_dof {expected}` (последние два вычисляются, когда появятся P3-T9/T10; пока статус `NOT_AVAILABLE`).
2. Результат `check_requirements`: по каждому — `{id, type, status: PASS|FAIL|STALE|NOT_AVAILABLE, measured, target, margin, hint}`. FEA-требования не пересчитываются автоматически (дорого): если результат устарел (`revision` изменился) — статус `STALE` и подсказка вызвать `run_fea_analysis`.
3. Опция `auto_check: true` в `set_requirements`: мутирующие инструменты (`add_feature_primitive`, `modify_feature`, `boolean_*`, `transform_part`, `cut_*`, `batch_cad_operations`) добавляют в ответ `requirements_status: {passed, failed, stale}` и список упавших.
4. Состояние требований сохраняется вместе с проектом (если есть P2-T4).

### Критерии приёмки
Тесты: габарит PASS/FAIL, масса, `mesh_valid`; пересчёт после `modify_feature` меняет статус; `STALE` после изменения детали при сохранённом FEA; `auto_check` добавляет сводку в ответ мутирующего инструмента; все существующие контрактные тесты проходят (поле в ответах — только добавляется).
