## ADR-001: Единый источник вычислений (Rust Backend) и тонкий веб-клиент (TypeScript)

### Контекст
В исходном состоянии репозитория геометрическое ядро, булевы операции CSG, МКЭ-решатель, кинематический симулятор, стоимостной оптимизатор DAG и диспетчер MCP (~7,9 тыс. строк) были продублированы на TypeScript в `src/cad/*.ts`. Реализации в Rust и TypeScript расходились по поведению, схемам и проверкам.

### Варианты
1. **Вариант А (Dual Engine)**: Поддерживать синхронно два движка (Rust для MCP, TypeScript в браузере).
2. **Вариант Б (Rust Single Source of Truth + HTTP/SSE/JSON-RPC API)**: Все расчёты (геометрия, DAG, CSG, тесселяция, валидация, оптимизатор, МКЭ, динамика механизмов) выполняются исключительно в едином процессе Rust (`mcp-cad-server`). Веб-клиент (React + Three.js) работает как тонкий терминал отображения и ввода, получая состояние сцены, полигональные сетки (`vertices`, `indices`, `normals`, поля напряжений МКЭ и кадры траекторий физики) и вызывая команды через единый диспетчер сервера.
3. **Вариант В (Rust в WASM + отдельный Rust MCP-сервер)**: Компилировать ядро в WebAssembly для браузера. Не решает проблему единого состояния между внешним ИИ-агентом (подключённым по stdio или HTTP к серверу) и браузером без серверной синхронизации.

### Выбор и обоснование
Выбран **Вариант Б**:
- Один процесс `mcp-cad-server` владеет `SharedState` (`Arc<RwLock<EngineState>>`).
- И внешние ИИ-агенты (по `stdio` или HTTP `/sse` + `/message`), и веб-интерфейс в браузере обращаются к одному и тому же слою команд (`dispatch_tool` + REST/SSE эндпоинты `/api/state`, `/api/events`, `/api/mcp`).
- Любое изменение детали или запуск симуляции ИИ-агентом мгновенно транслируется в открытый браузер через Server-Sent Events (`/api/events`), а любая правка пользователя в UI сразу видна ИИ-агенту при следующем запросе `list_parts` / `get_feature_tree` / `query_part_geometry`.
- Из TypeScript полностью удаляются вычислительные модули (`primitives.ts`, `csg_bsp.ts`, `fea_solver.ts`, `kinematics.ts`, `query_optimizer.ts`). В клиенте остаются только типы контрактов API, 3D-рендеринг Three.js, компоненты интерфейса и клиентский транспорт.

## ADR-002: Сетевая архитектура на порту 3000 и модель безопасности (`--auth-token`)

### Контекст
Среда предпросмотра (Preview) проксирует трафик на порт `3000` (`0.0.0.0:3000`). В то же время при запуске сервера на не-loopback интерфейсе (`0.0.0.0`) необходима защита MCP и всех мутирующих операций токеном авторизации (`Authorization: Bearer <TOKEN>`), тогда как по умолчанию без флагов сервер должен слушать локальный интерфейс `127.0.0.1`.

### Варианты
1. **Вариант А (Vite dev-сервер на 3000 + проксирование `/api`, `/sse`, `/message` на Rust-бэкенд + раздача собранной статики `dist/` самим Rust-сервером в standalone-режиме)**:
   - В режиме `npm run dev` запускается единый скрипт/процесс, поднимающий Rust-сервер и Vite (либо Rust-сервер непосредственно на порту 3000 с раздачей статики / проксированием).
2. **Вариант Б (Rust-сервер напрямую на порту 3000 или через Vite proxy с автоматической проброской dev-токена для UI и строгой проверкой `Authorization: Bearer` на бэкенде)**:
   - Rust-сервер по умолчанию биндится на `127.0.0.1`.
   - Попытка запуска `mcp-cad-server` с `--host 0.0.0.0` (или любым не-loopback IP) без `--auth-token` (или переменной окружения `MCP_CAD_AUTH_TOKEN`) завершается явной ошибкой старта.
   - При активном `--auth-token` все запросы к MCP (`/message`, `/sse`, `/api/mcp`) и все изменяющие состояние HTTP-запросы (`POST`, `PUT`, `DELETE` на `/api/*`) без заголовка `Authorization: Bearer <TOKEN>` (или с неверным токеном) отклоняются с кодом `401 Unauthorized`.

### Выбор и обоснование
Выбран **Вариант Б** с поддержкой как прямой раздачи статики `dist/` из `mcp-cad-server` на порту 3000, так и Vite proxy в dev-режиме:
- Обеспечивает работу Preview на порту 3000 и выполнение всех требований безопасности (отказ от привязки к `0.0.0.0` без токена, отклонение неавторизованных запросов с `401 Unauthorized`, подтверждённое автотестами).

## ADR-003: Изоляция нативного окна (`winit`) и серверный `capture_viewport` без физической GPU

### Контекст
Нативное окно `winit` в `mcp-cad-viewer` требует дисплейного сервера (Windows GUI / X11 / Wayland), который отсутствует в облачной headless-среде Linux, и тянет оконные зависимости в основной серверный бинарник. Инструмент `capture_viewport` и `get_fea_heatmap_image` должны надёжно работать на сервере без физической видеокарты.

### Варианты для `winit`
1. Вынести `window.rs` и зависимость `winit` под опциональный Cargo feature `native-gui` (по умолчанию выключен).
2. Полностью удалить `window.rs`.

### Выбор для `winit` и `capture_viewport`
- `winit` и `window.rs` вынесены под опциональный feature-флаг `native-gui`. В основном пути сборки (`default = []`) сервер не зависит от `winit`, а инструмент `open_preview_window` в headless-режиме валидирует аргументы (`part_id`) и возвращает статус синхронизации с веб-вьюпортом (`http://localhost:3000`).
- Для серверного рендеринга `capture_viewport` и `get_fea_heatmap_image` используется `wgpu` в headless-режиме поверх программного Vulkan-драйвера Mesa Lavapipe (`lvp_icd.x86_64.json`) с автоматическим fallback на CPU-растеризатор в `mcp-cad-viewer`, если в целевой системе нет ни аппаратного GPU, ни Lavapipe. Это гарантирует 100% работоспособность `capture_viewport` и `get_fea_heatmap_image` в любой среде (Linux container, CI, Windows без GPU).

### 1. Контекст и причины отказа от `rapier3d = "0.22"`

В фазах P0–P3 крейт `crates/mcp-cad-physics` использовал игровой движок `rapier3d = "0.22"` (`f32`, решатель импульсов `TGS-Soft`). В ходе реализации инженерных расчётов (`P3-T6` `get_part_load_cases`, `P3-T7` `run_fea_from_simulation`, `P3-T9` `analyze_mechanism`, `P3-T16` `sweep_joint`) выявлены фундаментальные ограничения `Rapier3D` для задач машиностроительного САПР:

1. **Одинарная точность (`f32`, машинный эпсилон $\approx 1.19 \times 10^{-7}$)**:
   - Потеря точности при малых зазорах, микроперемещениях и высоких отношениях масс/моментов инерции сопряжённых деталей.
   - Необходимость ручного поддержания дублирующих полей `gravity_f64` и проверок переполнения `f32::INFINITY` (`P2-T36`).
2. **Приближённый итерационный решатель `TGS-Soft` и податливость связей**:
   - На замкнутых кинематических контурах с избыточными планарными связями (четырёхзвенник и кривошипно-ползунный механизм: $\text{DOF}_{\text{grubler}} = -2$, $\text{DOF}_{\text{numeric}} = 1$, $3$ избыточные связи) последовательные релаксации Гаусса–Зейделя дают дрейф шарниров порядка $10^{-4}\text{..}10^{-3}\text{ м}$ и паразитные колебания реакций.
3. **Непрозрачное кодирование реакций шарниров (`compute_joint_world_wrench_on_part_a`)**:
   - Для извлечения физических сил $\mathbf{F}$ (Н) и моментов $\boldsymbol{\tau}$ (Н·м) для МКЭ (`P3-T6`) потребовался 280-строчный декодер внутренних импульсов `Rapier3D`, воспроизводящий деление шага `substep_dt = dt / num_substeps`, инверсию `body1 <-> body2` для статических опор (`JointOneBodyConstraintBuilder::generate`) и ортогонализацию Грама–Шмидта в пространстве обратной инерции (`finalize_constraints`).
4. **Отсутствие нативного ограничения зубчатой передачи (`CadJointType::Gear`)**:
   - В `Rapier3D 0.22` нет совместного скоростного/силового ограничения зубчатого зацепления. Временная реализация в `simulator.rs:580` принудительно перезаписывала угловую скорость ведомого колеса `rb_b.set_angvel(-ratio * w_a)` **после** шага решателя. В результате:
     - крутящий момент нагрузки с ведомого вала **не передавался** обратно на ведущий вал ($\tau_{\text{motor},1} = 0$ при любой внешней нагрузке $\tau_{\text{load},2}$);
     - в `joint_reactions` для зубчатой пары возвращались нули.
5. **Огрубление геометрии и инерции через `ConvexHull`**:
   - По умолчанию динамические тела получали масс-инерционные характеристики от выпуклой оболочки `ConvexHull`, игнорирующей сквозные отверстия, выточки и полости детали `Part`.

### 2. Рассмотренные архитектурные кандидаты (`f64` на базе `nalgebra`)

Во всех кандидатах состояние $N$ подвижных твёрдых тел описывается в двойной точности `f64`:
- **Обобщённые координаты позы** $\mathbf{q} \in (\mathbb{R}^3 \times SO(3))^N$: положение центра масс $\mathbf{x}_i \in \mathbb{R}^3$ (или начала локальной СК $\mathbf{p}_i$) и единичный кватернион ориентации $\mathbf{q}_i \in \mathbb{H}_1$ ($R_i \in SO(3)$).
- **Обобщённые скорости** $\mathbf{v} \in \mathbb{R}^{6N}$: вектор $[\mathbf{v}_1^T, \boldsymbol{\omega}_1^T, \dots, \mathbf{v}_N^T, \boldsymbol{\omega}_N^T]^T$ в мировой системе координат.
- **Блочно-диагональная матрица масс и инерции** $M(\mathbf{q}) = \operatorname{diag}(m_1 I_3, I_{w,1}, \dots, m_N I_3, I_{w,N}) \in \mathbb{R}^{6N \times 6N}$, где $I_{w,i} = R_i I_{\text{loc},i} R_i^T$.

#### Кандидат A (Выбран): Прямой регуляризованный KKT-решатель индекса-2 на уровне скоростей/ускорений с трапецеидальным шагом и Gauss–Newton SVD проекцией координат (`DirectKktIndex2Projection`)

1. **Предиктор свободных скоростей (Ньютон–Эйлер с гироскопическим членом)**:
   $$\mathbf{v}^* = \mathbf{v}_k + M^{-1} \left(\mathbf{f}_{\text{ext}} - \begin{bmatrix} \mathbf{0} \\ \boldsymbol{\omega}_k \times (I_w \boldsymbol{\omega}_k) \end{bmatrix}\right) \Delta t.$$
2. **Формулировка ограничений на уровне скоростей и кривизны траектории ($\dot{J}\mathbf{v}$)**:
   - Собирается глобальный якобиан связей $J(\mathbf{q}_k) \in \mathbb{R}^{m \times 6N}$ (совместимый с `CadJointType::fill_jacobian_rows` из `P3-T9`, включая строки `Fixed` (6), `Revolute` (5 + упор/мотор), `Prismatic` (5 + упор/мотор), `Spherical` (3) и **прямую строку `Gear` (1)**: $r\,\hat{\mathbf{z}}_a^T \boldsymbol{\omega}_a + \hat{\mathbf{z}}_b^T \boldsymbol{\omega}_b = 0$).
   - В правую часть $\mathbf{b}_{\text{rhs}}$ сферических, вращательных и жёстких шарниров включается точная центростремительная поправка кривизны второго порядка:
     $$(\dot{J}\mathbf{v})_{\text{lin}} = \boldsymbol{\omega}_a \times (\boldsymbol{\omega}_a \times \mathbf{r}_a) - \boldsymbol{\omega}_b \times (\boldsymbol{\omega}_b \times \mathbf{r}_b), \quad \mathbf{b}_{\text{rhs}} = -\dot{J}\mathbf{v}_k\,\Delta t.$$
     Благодаря этому на вращающихся звеньях решатель сразу выдаёт **точную** центростремительную реакцию $F_r = -m\omega^2 r_c$ без запаздывания по фазе и без паразитного дрейфа.
3. **Прямое решение регуляризованной системы KKT / дополнения Шура с Box-LCP ограничениями**:
   - Формируется симметричная положительно определённая матрица Делассю (дополнение Шура):
     $$A = J M^{-1} J^T + \epsilon_{\text{CFM}} \cdot \max_i(A_{ii})\,I_m, \quad \epsilon_{\text{CFM}} = 10^{-10}.$$
   - Регуляризация Тихонова / CFM ($\epsilon_{\text{CFM}} = 10^{-10}$) гарантирует невырожденность и гладкое распределение нагрузок на пространственно переопределённых плоских механизмах (например, четырёхзвенник и кривошипно-ползунный механизм с 3 избыточными связями, где $\operatorname{rank}(J) = 17 < 20$).
   - Для двусторонних голономных связей и неголономной передачи `Gear` ($\lambda_i \in (-\infty, +\infty)$) система $A\,\boldsymbol{\Delta\Lambda} = \mathbf{b}_{\text{rhs}} - J\mathbf{v}^*$ решается **напрямую** разложением Холецкого ($LL^T$, с SVD-резервом).
   -При наличии активных односторонних упоров `limits` ($\lambda_i \ge 0$ или $\lambda_i \le 0$) и приводов `MotorConfig` с ограничением момента/силы ($\lambda_i \in [-F_{\max}\Delta t, +F_{\max}\Delta t]$) применяется метод активного множества (Active-Set Box-LCP) поверх прямого решателя $A_{FF}$.
   - Физические реакции каждого шарнира извлекаются напрямую из найденного вектора множителей Лагранжа:
     $$\boldsymbol{\lambda} = \frac{\boldsymbol{\Delta\Lambda}}{\Delta t} \implies \mathbf{F}_{A \leftarrow B}, \;\boldsymbol{\tau}_{A \leftarrow B}$$
     с автоматическим выполнением III закона Ньютона ($\mathbf{F}_{A \leftarrow B} = -\mathbf{F}_{B \leftarrow A}$) с машинной точностью $\sim 10^{-15}$.
4. **Трапецеидальный (Midpoint) шаг интегрирования позы**:
   $$\mathbf{v}_{k+1} = \mathbf{v}^* + M^{-1} J^T \boldsymbol{\Delta\Lambda}, \quad \mathbf{v}_{\text{mid}} = \frac{1}{2}(\mathbf{v}_k + \mathbf{v}_{k+1}),$$
   $$\mathbf{x}_{\text{com}, k+1} = \mathbf{x}_{\text{com}, k} + \mathbf{v}_{\text{lin,mid}}\,\Delta t, \quad \mathbf{q}_{k+1} = \exp\left(\frac{1}{2}\boldsymbol{\omega}_{\text{mid}}\,\Delta t\right) \otimes \mathbf{q}_k.$$
   Трапецеидальное правило 2-го порядка даёт **нулевую ошибку интегрирования** на равноускоренном движении (свободное падение $y(t) = y_0 + v_0 t + \frac{1}{2}gt^2$ воспроизводится с точностью `~1e-15 м`).
5. **Нелинейная проекция координат на многообразие связей $\Phi(\mathbf{q}) = \mathbf{0}$ (Index-2/Index-3 Manifold Projection)**:
   - После обновления позы выполняется 1–3 шага демпфированной проекции Гаусса–Ньютона через SVD (единая математическая база с `ClosedLoopSolver` из `P3-T16`):
     $$J(\mathbf{q})\,\Delta\mathbf{q} = -\Phi(\mathbf{q}),$$
     устраняющей любой геометрический дрейф замкнутых петель и зубчатых передач до уровня $\|\Phi(\mathbf{q})\|_\infty < 10^{-13}\text{ м/рад}$ без искусственного впрыска энергии, присущего методу Баумгарте.

#### Кандидат B: Полунеявный Эйлер + Итерационный Projected Gauss–Seidel (PGS) со стабилизацией Баумгарте (`SemiImplicitEulerPgsBaumgarte`)
- Классический игровой подход, переведённый в `f64`: решает систему импульсов покоординатными итерациями PGS ($N_{\text{iter}} = 60$) с добавлением позиционной невязки $\frac{\beta}{\Delta t}\Phi(\mathbf{q}_k)$ ($\beta = 0.25$) в правую часть скоростей и обновляет координаты по схеме симплектического Эйлера 1-го порядка ($\mathbf{x}_{k+1} = \mathbf{x}_k + \mathbf{v}_{k+1}\Delta t$).
- **Недостатки, выявленные на бенчмарках**:
  - На свободном падении схема Эйлера 1-го порядка даёт систематическую ошибку положения $\frac{1}{2}|g|\Delta t\,T = 24.5\text{ мм}$ за $1\text{ с}$ при $\Delta t = 5\text{ мс}$.
  - На замкнутом кривошипно-ползунном контуре с 3 избыточными связями PGS сходится медленно, оставляя невязку замыкания $\sim 10^{-4}\text{ м}$, а член Баумгарте вносит фазовое возмущение в скорости и реакции.

#### Кандидат C: Метод штрафных функций / регуляризованных пружин (Penalty Method)
- Заменяет голономные связи $\Phi(\mathbf{q}) = 0$ жёсткими виртуальными пружинами $\mathbf{F}_c = -k_p \Phi(\mathbf{q}) - c_d J\mathbf{v}$.
- **Причина отклонения**: требует малого шага $\Delta t \ll \sqrt{m / k_p}$ и порождает высокочастотные паразитные осцилляции реакций, неприемлемые для передачи нагрузок в МКЭ (`run_fea_from_simulation`).

### 4. Утверждённая целевая архитектура и схема данных для `P4-T2`–`P4-T6`

На основании результатов бенчмарков утверждается **Кандидат A (`DirectKktIndex2Projection`)** со следующей модульной структурой в `crates/mcp-cad-physics`:

1. **`rigid_body.rs` (`P4-T2`)**:
   - Собственные типы `BodyHandle(pub usize)`, `ColliderHandle(pub usize)`, `RigidBody` и `Collider` в `f64` без зависимостей от `rapier3d`.
   - Точный аналитический расчёт объёма, центра масс $\mathbf{c}_{\text{loc}}$ и полного $3\times 3$ тензора инерции $I_{\text{loc}}$ по замкнутой триангулированной сетке `TriangleMesh` методом знаковых тетраэдров относительно начала координат (с точным учётом всех внутренних отверстий, пазов и полостей).
   - Геометрические примитивы коллайдеров `ColliderShape` в `f64` (`ConvexHull`, `TriMesh`, `Compound`, `Cube`, `Sphere`, `Cylinder`) с кэшированием локального и мирового `BoundingBox`.
2. **`solver.rs` (`P4-T3`, на базе `dae_prototype.rs`)**:
   - Прямой регуляризованный KKT-решатель $(J M^{-1} J^T + \epsilon I)\,\boldsymbol{\Delta\Lambda} = \mathbf{b}_{\text{rhs}} - J\mathbf{v}^*$ с поддержкой всех 5 типов шарниров (`Fixed`, `Revolute`, `Prismatic`, `Spherical`, `Gear`), активных упоров `limits`, моторов `MotorConfig`, центростремительной поправки $-\dot{J}\mathbf{v}$, трапецеидального шага и SVD-проекции координат $\Phi(\mathbf{q}) = \mathbf{0}$.
3. **`collision.rs` (`P4-T4`)**:
   - Конвейер обнаружения столкновений в `f64` (Broad-phase AABB + Narrow-phase аналитика / GJK-EPA / TriMesh) с односторонними контактными ограничениями ($\lambda_n \ge 0$), сухим трением Кулона ($|\lambda_t| \le \mu \lambda_n$) и генерацией `CollisionRecord` (`Started` / `Stopped`).
4. **Прямой экспорт реакций в FEA (`P4-T5`)**:
   - Прямое чтение вектора сил `last_force_on_a` и моментов `last_torque_on_a` из множителей Лагранжа $\boldsymbol{\lambda}$ решателя в `joint_reaction_force` и `extract_part_load_case`, с полным удалением 280-строчного декодера импульсов `Rapier3D`.
