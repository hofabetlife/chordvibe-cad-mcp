## ADR-001: Единый источник вычислений (Rust Backend) и тонкий веб-клиент (TypeScript)

### Контекст
В исходном состоянии репозитория геометрическое ядро, булевы операции CSG, МКЭ-решатель, кинематический симулятор, стоимостной оптимизатор DAG и диспетчер MCP (~7,9 тыс. строк) были продублированы на TypeScript в `src/cad/*.ts`. Реализации в Rust и TypeScript расходились по поведению, схемам и проверкам.

### Варианты
1. **Вариант А (Dual Engine)**: Поддерживать синхронно два движка (Rust для MCP, TypeScript в браузере).
2. **Вариант Б (Rust Single Source of Truth + HTTP/SSE/JSON-RPC API)**: Все расчёты (геометрия, DAG, CSG, тесселяция, валидация, оптимизатор, МКЭ, динамика механизмов) выполняются исключительно в едином процессе Rust (`mcp-cad-server`). Веб-клиент (React + Three.js) работает как тонкий терминал отображения и ввода, получая состояние сцены, полигональные сетки (`vertices`, `indices`, `normals`, поля напряжений МКЭ и кадры траекторий физики) и вызывая команды через единый диспетчер сервера.
3. **Вариант В (Rust в WASM + отдельный Rust MCP-сервер)**: Компилировать ядро в WebAssembly для браузера. Не решает проблему единого состояния между внешним ИИ-агентом (подключённым по stdio или HTTP к серверу) и браузером без серверной синхронизации.

### Выбор и обоснование
Выбран **Вариант Б**:
- Один процесс `mcp-cad-server` владеет `SharedState` (`Arc<RwLock<EngineState>>`).
- И внешние ИИ-агенты (по `stdio` или HTTP `/sse` + `/message`), и веб-интерфейс в браузере обращаются к одному и тому же слою команд (`dispatch_tool` + REST/SSE эндпоинты `/api/state`, `/api/events`, `/api/mcp`).
- Любое изменение детали или запуск симуляции ИИ-агентом мгновенно транслируется в открытый браузер через Server-Sent Events (`/api/events`), а любая правка пользователя в UI сразу видна ИИ-агенту при следующем запросе `list_parts` / `get_feature_tree` / `query_part_geometry`.
- Из TypeScript полностью удаляются вычислительные модули (`primitives.ts`, `csg_bsp.ts`, `fea_solver.ts`, `kinematics.ts`, `query_optimizer.ts`). В клиенте остаются только типы контрактов API, 3D-рендеринг Three.js, компоненты интерфейса и клиентский транспорт.

## ADR-002: Сетевая архитектура на порту 3000 и модель безопасности (`--auth-token`)

### Контекст
Среда предпросмотра (Preview) проксирует трафик на порт `3000` (`0.0.0.0:3000`). В то же время при запуске сервера на не-loopback интерфейсе (`0.0.0.0`) необходима защита MCP и всех мутирующих операций токеном авторизации (`Authorization: Bearer <TOKEN>`), тогда как по умолчанию без флагов сервер должен слушать локальный интерфейс `127.0.0.1`.

### Варианты
1. **Вариант А (Vite dev-сервер на 3000 + проксирование `/api`, `/sse`, `/message` на Rust-бэкенд + раздача собранной статики `dist/` самим Rust-сервером в standalone-режиме)**:
   - В режиме `npm run dev` запускается единый скрипт/процесс, поднимающий Rust-сервер и Vite (либо Rust-сервер непосредственно на порту 3000 с раздачей статики / проксированием).
2. **Вариант Б (Rust-сервер напрямую на порту 3000 или через Vite proxy с автоматической проброской dev-токена для UI и строгой проверкой `Authorization: Bearer` на бэкенде)**:
   - Rust-сервер по умолчанию биндится на `127.0.0.1`.
   - Попытка запуска `mcp-cad-server` с `--host 0.0.0.0` (или любым не-loopback IP) без `--auth-token` (или переменной окружения `MCP_CAD_AUTH_TOKEN`) завершается явной ошибкой старта.
   - При активном `--auth-token` все запросы к MCP (`/message`, `/sse`, `/api/mcp`) и все изменяющие состояние HTTP-запросы (`POST`, `PUT`, `DELETE` на `/api/*`) без заголовка `Authorization: Bearer <TOKEN>` (или с неверным токеном) отклоняются с кодом `401 Unauthorized`.

### Выбор и обоснование
Выбран **Вариант Б** с поддержкой как прямой раздачи статики `dist/` из `mcp-cad-server` на порту 3000, так и Vite proxy в dev-режиме:
- Обеспечивает работу Preview на порту 3000 и выполнение всех требований безопасности (отказ от привязки к `0.0.0.0` без токена, отклонение неавторизованных запросов с `401 Unauthorized`, подтверждённое автотестами).

## ADR-003: Изоляция нативного окна (`winit`) и серверный `capture_viewport` без физической GPU

### Контекст
Нативное окно `winit` в `mcp-cad-viewer` требует дисплейного сервера (Windows GUI / X11 / Wayland), который отсутствует в облачной headless-среде Linux, и тянет оконные зависимости в основной серверный бинарник. Инструмент `capture_viewport` и `get_fea_heatmap_image` должны надёжно работать на сервере без физической видеокарты.

### Варианты для `winit`
1. Вынести `window.rs` и зависимость `winit` под опциональный Cargo feature `native-gui` (по умолчанию выключен).
2. Полностью удалить `window.rs`.

### Выбор для `winit` и `capture_viewport`
- `winit` и `window.rs` вынесены под опциональный feature-флаг `native-gui`. В основном пути сборки (`default = []`) сервер не зависит от `winit`, а инструмент `open_preview_window` в headless-режиме валидирует аргументы (`part_id`) и возвращает статус синхронизации с веб-вьюпортом (`http://localhost:3000`).
- Для серверного рендеринга `capture_viewport` и `get_fea_heatmap_image` используется `wgpu` в headless-режиме поверх программного Vulkan-драйвера Mesa Lavapipe (`lvp_icd.x86_64.json`) с автоматическим fallback на CPU-растеризатор в `mcp-cad-viewer`, если в целевой системе нет ни аппаратного GPU, ни Lavapipe. Это гарантирует 100% работоспособность `capture_viewport` и `get_fea_heatmap_image` в любой среде (Linux container, CI, Windows без GPU).
